Paper #57

(Download paper of type application/pdf )

Title: Design, Analysis, and Implementation of Virtual IO
Abstract: In this paper we propose Virtual IO, which divides an
IO request into small temporal units of disk commands
for enabling preemptible disk access. We present our
main design strategies, analyze Virtual IO&#039;s performance,
and describe implementation challenges. Our evaluation
shows that Virtual IO substantially reduces IO waiting
time with little or no loss in disk throughput.

Provide a short summary of the paper and its contributions This paper presents a method for reducing the
waiting time that an I/O encounters due to a lower priority I/O being in progress. The idea is elegantly simple: many I/Os can be decomposed into shorter operations so that a higher priority request can, in effect, preempt an I/O between any two of these micro operations. For example, a long seek can be decomposed into 2 smaller seeks; a long read can be decomposed into a series of small reads (for which we assume that track buffers hide any additional latency). I kind of like the idea in its simplicity, but I fear it has limited applicability: real time systems rarely seem to incorporate I/O in my experience. The other example cited, that of video editing doesn't seem to be one where various disk I/Os have different priorities.

It seems that the idea of breaking up long transfers has been presented earlier, but these folks also figure out how to make seeks and rotational delay preemtible, which is also useful.

There isn't anything deep here, but it's a nice,
simple technique, and it seems that it may be useful in a limited number of circumstances.
Provide detailed, construtive comments to the author The equation and derivation on page 4 are identical to those in the Introduction. This is probably the right place to introduce this explanation, so it should be omitted from the introduction. In fact, much of the discussion has already been done in the Introduction. Either reduce the introduction or
remove it from this section.

On page 5, the claim is made that "for the range of chunk sizes, the disk throughput using chunking is optimal with negligble CPU overhead." What range? I had the same question when I saw this same thought in the introduction ...

Given that section 3 refers repeatedly to the disk profiler, perhaps it makes sense to describe it first, before going into the various mechanisms used for decomposing operations into "micro-operations."

I'm not sure I agree with the statement on page 6 that it is OK for the disk to report a write complete once the data is in the write-buffer. This is exactly what IDE disks do and as a result, it is virtually impossible to use them for
highly reliable data storage (i.e., transactional data storage). This is really a problem for some applications and should not be glossed over so lightly. It's OK to say that you only target such devices, but it's not OK to
simply say that you can consider them done when they are in the write buffer.

Review #152 For Paper #57
(review last modified Saturday 12th of October 2002 06:39:13 PM)
Attribute Value
Provide a short summary of the paper and its contributions Summary: The authors present the idea of "virtual I/O", a method of breaking each high-level disk I/O operation (ie "read block X") into a series of lower-level operations (ie "seek halfway to the track block X is in", "seek the rest of the way to the track block X is in", "wait for block X to rotate under the head", and "read block X"), providing the opportunity for the high-level operation to be preempted and rescheduled. Traditionally operations like "read block X" are treated as invisible operations. By breaking disk operations into a series of shorter (but still indivisible) operations, there are more rescheduling opportunities if a higher-priority request comes along in the meanwhile, or if a new request can be efficiently interleaved with the current request. They benchmark their implementation for several trace-based workloads.
Provide detailed, construtive comments to the author Comments: An interesting new application of a set of ideas that
people have been playing with for a few years. Reminded me quite a
bit of Lumb, Schindler, Ganger, Nagle, and Riedel's paper from OSDI
2000 "Towards higher disk head utilization: Extracting Free bandwidth
from busy disk drives" and Lumb, Schindler, and Ganger's "Freeblock
Scheduling Outside of Disk Firmware" (FAST 2002, cited by this paper),
but addresses a different problem.

This paper has two important "stylistic" problems that might drive
readers away before they have a chance to figure out what this paper
is really about.

The first is the term "virtual IO", which confused me greatly until I
understood what it means-- but I still think it's simply a bad (if not
misleading) name for this concept. There's nothing virtual about the
IO-- it's the same as it always was. Perhaps something like
"preemptible I/O" or "staged I/O" (although "staged" has other
meanings as well).

The second is an unfortunate choice of wording in the introduction.
When I read the sentence "Traditionally, disk IOs have been thought of
as blocking operations." my first reaction was incredulity and a
sinking feeling that the paper wasn't going to make any sense, since
the OSs that I think of as "traditional" haven't blocked on I/O
operations for decades. It wasn't until a read a little further that
I understood the point-- this sentence is talking about the fact that
only one I/O is issued at a time PER DISK-- but even that statement
isn't really true! Contemporary disks and controllers are intelligent
enough to manage their own scheduling, and most enlightened OSs let
them do it. Tagged queuing has been around for a while in the SCSI
world, and is started to appear in different guises in IDE drives.
Eventually the point *is* made clear in the text, but if I was a
casual but skeptical reader, I might have set aside the paper already,
thinking that it addresses a problem that doesn't really exist any
more, and never really understanding what the paper is truly about.
Perhaps I am only betraying how superficial a reader I am, but I do
think this could be improved.

Now, on the to the technical aspects...
I expect that some aspects of this idea, especially seek-splitting,
have an effect on the overall power use of the disk. Breaking seeks
into sub-seeks increases the proportion of the time the actuator will
be accelerating/decelerating the head. If you break the seeks into
small enough pieces, you'll be at maximum power during the entire seek
(instead of accelerating up to maximum velocity, traveling at this
velocity for a while, and then decelerating). Seeking is a high-power
operation. I'm interested in the impact this will have in terms of
both power consumption and disk wear. Can you show the change in
power consumption for each configuration?

Drives intended for laptops or desktops often have different firmware
than the identical drives intended for server use. In particular,
these drives often have special heuristics to "smooth" seeks instead
of accelerating at maximum velocity, because fast seeks make the disk
noisy and cause vibration, which people don't like. How does this
interact with your method (or are you assuming that this is only for
servers)?

Please describe the parameters of the disks being tested earlier
(before figure 5). The SCSI disk is described on the next page. I
don't remember seeing the IDE disk described anywhere.

In the structure of the paper, it feels like there is considerable
repetition between the introduction, the first part of section 3, and
the subsections of 3.

For the trace-based benchmarks, how is the "priority" of the disk
accesses stored? I'd like to know a lot more about these traces-- how
many operations are there per trace? How much time was spent in
priority inversions? What effect on the overall system performance
does the reduction in the expected waiting time have? Using virtual
IO can slow down normal-priority operations (by 10% or less, according
to the traces)-- when is it worthwhile to have most operations go 10%
slower in order to make a small number high-priority operations
somewhat faster? I don't feel like I know enough about the trade-offs
to decide whether I want this on my own server-- what would I need to
measure in order to figure this out? (I know this is a difficult set
of question to answer, but I think they are critical.)

Typos:

All the "T_{transfer}" things should be changed because the f in
"transfer" is treated differently in math mode, so it looks more like
"trans f er".

Figure 12: "logaritmic scale" -> logarithmic scale"

Provide a short summary of the paper and its contributions The paper proposes several ways to make IOs more
preemptible. 1. divide the data transfer into
several smaller chunks. 2. split up a long seek
into several shorter ones. 3. Use just-in-time
seeking to shift the time the disk spends waiting
for the right sector to reach the disk head. The
only mechanism that costs additional time is
splitting up a long seek (since disk heads waste
time during the beginning and end of each shorter
seek). The paper also describes using the JIT-seek
technique to do other useful work, such as
prefetching.
Provide detailed, construtive comments to the author I recommend the authors drop the
discussion of prefetching--it's tangential to the
main point of the paper, which is enabling
preemption to reduce the waiting time of higher
priority requests. It it also somewhat unfair to
use free prefetching to offset the cost of
virtual IO, since free prefetching could just as
well be applied to non-preemptible IO. The point
of the paper is that IO can be made preemptible
at low overhead, not that the overhead of
preemptibility can be masked by general
techniques.

This is a nice paper. None of the techniques by
themselves are particularly novel, but the paper
does a good job combining the techniques to
achieve a high degree of preemptibility.

Please state more clearly in the example on page
2 that the seek splitting doesn't cause overhead
IN THIS CASE (since it can be masked by Trot).
The paper does say this later, but it should be
in the first discussion (page 2, column 2,
paragraph 2).

Footnote 3 on page 2 is essential to a proper
understanding of the paper. It belongs in a
prominent place early in the main text.

Suggest you change the term "virtual IO" to
"preemptible IO", since virtual connotes
something a bit different (at least to this
reader).

Provide a short summary of the paper and its contributions This paper describes an approach to breaking time-consuming disk requests
into smaller pieces without increasing their completion time. It does
this by exploiting detailed knowledge of the disk timings and mechanisms.
By doing so, it significantly reduces the amount of time that a
higher-priority I/O request would have to wait, simulating a degree of
preemptability for disk I/O.
Provide detailed, construtive comments to the author I like the idea, and the work seems solid. The writing needs work, but
I think this paper should be accepted.

First, and perhaps foremost, please don't use "Virtual I/O" as the name.
Worse than not being descriptive, it confuses one. Perhaps "fractured I/O",
"Semi-preemptable I/O", or some other useful term.

Be careful of over-statement: it does not "enable preemptible disk access"
(abstract) or "provide highly preemptible disk access" (intro).

The writing is excessively repetitive. For example, it says that it
"proposes Virtual I/O, which does X" perhaps a half-dozen times. Also,
it seems like [7] is referenced every time Diskbench is mentioned.

The authors need to spend more effort on discussing how previous work
in low-level disk stuff relates. For example, the various disk profiling
activities provide the necessary tools, but are mentioned as an afterthought
(also, add Aboutabl etal (sigmetrics 1998), and Worthington etal (sigmetrics
1995)). Systems like that described by Yu etal (OSDI 2000, and their
related work) should be mentioned. Finally, Lumb etal (in the OSDI 2000
paper that predated [12]) describe free prefetching, and even coin the
same name for it.

Do you have any insight into the bug that results in the effect described
in 3.1.1 and shown in Figure 3?

Significant additional detail is needed in the description of the
experimental setup, including a bit more info about the disk and a
lot more information about the simulated and traced workloads. At
least for the simulated workload, the metric should be "have I told
readers enough to let them recreate my experiments".

Explain and discuss the "free prefecthing" parts of the bars. In
particular, I wasn't sure if they represented potential or actual
bandwidth improvement experienced by the application.
